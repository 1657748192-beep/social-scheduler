# 内置时区规则与自动更新详细设计

日期：2026-10-20。状态：用户已确认设计与实施计划，本地实现及验证完成，未部署。本文保留设计阶段的审批边界，实际验证见 `docs/managed-timezone-rules-verification.md`。

## 目标和已确认边界

默认使用电脑所处时区填写新的单次排程，允许选择国家／代表城市，保留当地时间与北京时间双预览。全部地区统一使用软件内置的免费 IANA 时区规则，不再混用“多数地区使用浏览器、五个地区使用补丁”的模式。自动检查规则更新，验证成功后启用，失败继续使用最近有效版本。

“电脑右下角时间”只表示默认时区和用户熟悉的钟面，不把电脑时钟作为发布执行依据。服务器仍执行已确定的 UTC 时刻。原有排程、平台发布权限、凭据、账号、会员限制和队列格式不变，不重启 Worker。不购买服务、不增加云资源；复用现有 API、网页和存储。网络流量和磁盘有小幅实际开销，免费数据不代表绝对零资源消耗；超过现有资源／免费额度就停止启用并报告，不能自行开通收费资源。

本设计是原《全球时区定时发布详细设计》的增补，仅替换默认时区、规则换算和规则更新机制；其他交互、权限和历史数据保护约束继续有效。批准本文后再编写实施计划，当前不把方案方向确认视为代码实施或部署授权。

## 方案比较与选择

1. 浏览器 Intl：体积小，但不同浏览器数据库版本不同，无法解决已发现的规则落后问题，不采用作为换算来源。
2. 仅五个地区补丁：维护两套规则且其他地区仍可能过时，不采用。
3. 软件统一携带版本化规则并受控更新：选用此方向。首选经过许可证、漏洞、体积检查的 Moment Timezone 数据引擎及完整年份 packed 数据；其 zone 转换表可以独立加载，不依赖电脑内置偏移规则。具体依赖版本和首版规则版本在实施计划前锁定并核验，不承诺未核实的软件包已包含最新 IANA 版本。

不直接使用库的“缺失时间自动顺延／重复时间默认选一次”行为。转换适配层负责严格求解，库负责读取官方转换表，不手写五个地区的偏移例外。Luxon 可继续承担不涉及时区规则的既有职责；本功能所有 UTC→当地、当地→UTC、当地今天和预览偏移必须统一走新适配层。

## 默认值与会话稳定性

只在新建空表单初始化时读取 `Intl.DateTimeFormat().resolvedOptions().timeZone`，通过内置数据的规范标识或别名表校验。识别失败回退 Asia/Shanghai，界面显示当前默认地区。新开草稿和复制内容使用同一初始化规则，不复用原任务的过去时间。

不得在 SSR 阶段采用服务器时区。客户端识别前禁止提交定时任务；用户已开始输入或选择地区后，迟到的初始化不得覆盖输入。电脑时区在会话中改变不自动修改当前表单；下一次新建会话重新读取。编辑已有任务始终使用原任务时区与实际时刻，不采用电脑默认值。

日历格子、日期分组和拖拽继续使用北京时间，并保留可见标注；本轮不是整站时区迁移。

## 数据版本和求解契约

每个规则包包含 schemaVersion、engineCompatibility、tzdbVersion、来源、生成时间、数据摘要、完整规则与别名。网页内置经过核验的基线规则包，首次访问或离线不必等待外部服务。使用完整可用年份，不采用会在年份边界静默套用最后偏移的十年裁剪数据；引擎不能保证的日期范围必须明确拒绝。

适配层接受不可变规则快照：同一快照生成输入解析、候选 UTC、双预览、提交值及偏移。严格校验公历年月日时分，对转换表中的可能偏移生成候选 UTC，按该候选处有效区间验证并回读；去重排序后，零候选表示不存在，两个候选要求人工选择，异常更多候选阻止提交。不能假设变化恰好一小时。保留旧 UTC 秒和毫秒；只有用户重新选择分钟时才归零。

不根据浏览器偏移决定五个地区是否可用。改为检查规则包版本、数据结构、完整性、引擎兼容和转换样例；不通过时回退已验证基线，不把不可信输入直接加载到全局引擎。所有规则包仅数据 JSON，严禁远程脚本、eval、动态 npm 安装或自动执行下载代码。

## 自动检查、下载与启用

由 API 进程承担有界规则维护，不使用 Worker、BullMQ、新 cron、外部自动化或新服务。API 启动非阻塞检查，并每 24 小时检查一次，失败按有限退避重试；超时、下载上限和关闭清理均有硬限制。多实例通过现有 Redis 锁避免重复下载，不修改发布队列键。测试默认不启动真实下载或定时器。

检查官方 IANA 发布版本，同时检查固定可信发布方提供的预编译规则数据。上游编译包落后于 IANA 时，保留最近已验证版本并报告“上游规则待更新”，不能声称已经最新，也不在生产服务器临时编译或执行上游工具。首版必须核验实际数据覆盖已发现的五个地区变更，否则不能通过验收。

来源域名、包名和 HTTPS 路径固定，不允许用户提供下载地址；禁止任意重定向、私网地址及 tar 路径穿越。以可信发布元数据校验传输完整性，再独立校验 JSON schema、转换区间排序、范围、别名循环、地区覆盖、版本单调性和回归样例。摘要只证明一致性，不冒充发布者签名。新引擎才能解释的数据不得自动启用，必须等待常规软件升级。

复用现有 Redis 的独立 `timezone-rules:v1:` 命名空间缓存数据，不使用公开 uploads 路径，不增加挂载、不改 Worker 环境。每个解压后 JSON 包最多 4 MiB，最多缓存 active、previous 和一个临时包，总数据上限 12 MiB；实施前测量现有 Redis 容量，若不满足余量要求则不启用自动缓存，不扩容。完整验证后以事务原子切换 active manifest。Redis 不可用、缓存被淘汰或服务重启丢失缓存时使用软件内置基线，恢复后重新检查；不把缓存承诺为永久存储，也不允许整个 Redis 清库。

只保留两个缓存版本、一个临时下载，按硬大小上限清理本功能自己的键。检查日志不包含用户身份、帖子或令牌；失败不会影响 API 启动、发布接口或既有排程。

## 网页获取与不中途改时

新增只读、登录后可访问的规则 manifest 和指定版本数据接口，通过现有 API 提供，无用户可控路径，无写入或远程更新触发接口，限流并支持 ETag。普通客户不展示技术信息；管理员可查看当前版本、最近检查和异常状态。网页资源缓存故障不影响使用内置规则。

新编辑会话优先加载已验证 active 版本，网络失败使用内置基线或兼容且再次验证的本地缓存。每个表单锁定一份快照；后台发现新版本不能重新解释已输入当地时间，也不能替用户更换重复时刻选择。界面提示“时区规则已更新，下次新建排程使用”；用户关闭当前表单后再创建时启用新版。

已保存排程和队列仅按原 UTC 执行，不因规则更新重排。历史详情可按当前有效规则重新显示当地时间，但 UTC 和北京时间的实际时刻不改变，必要时提示政策变化可能影响当地显示。只读查看、切换显示时区、规则更新都不发改期请求；文本保存仍省略 timezone。无需新表、数据迁移、回填或重建队列。

API 保存已有明确 UTC 和有效时区标识，不二次换算。新旧规则之间的差别不能由服务器静默“修正”为其他实际时刻。引擎支持但 API 运行环境不认识的新标识必须通过受控规则目录校验兼容，不能以任意字符串放宽现有安全约束。

## 验收与保护

- 保留原全部数学、组件和真实 HTTP／存储／队列回归，包含缺失小时、重复小时、半小时切换、45 分钟偏移、整日跳变及日期线。
- 在浏览器 Intl 故意返回旧偏移或不能转换时，内置规则仍产生独立、正确的已核验 UTC；五个已知地区分别以官方版本样例验收，不测试代码自己计算的期望值。
- 不同电脑默认时区分别初始化；SSR、读取失败、初始化迟到、用户先输入、切工作区、旧任务编辑都不覆盖已确定状态。
- 规则更新的正常检查、上游落后、断网、超时、错误摘要、坏 JSON、过大数据、恶意别名、降级包、锁竞争、Redis 容量不足／故障／淘汰、原子切换中断、重启恢复、停机清理均有独立测试。
- 表单打开期间更新不改变预览、选择与提交；下一会话使用新规则，旧任务 UTC、秒毫秒、权限、凭据、数据库记录与 Redis 发布任务完整内容不变。
- 检查依赖许可证、生产漏洞和网页增量体积；执行完整测试、API／网页构建、移动端与键盘操作验证。仅在独立本地测试环境造任务，不实际发布社媒内容。

## 部署边界

本轮仅详细设计，不安装依赖、实施产品代码、推送或部署。实施计划明确 API 和网页的兼容顺序及规则缓存容量核查；后续部署必须单独批准，只更新 API 和网页，Worker 不构建、不重启，原权限、凭据、排程和收费配置不变。回退使用 previous 或内置基线，不恢复／删除用户已确认排程。

## 资料依据

- IANA 官方数据库与版本公告：https://www.iana.org/time-zones （本次核查显示 2026e）。规则会随政策变化，更新检查不能保证上游永远即时提供新政策。
- Moment Timezone 数据加载与 zone 对象：https://momentjs.com/timezone/docs/ 。可加载独立数据；必须规避默认顺延和歧义选择，完整数据体积在实施前实测。

自审结论：默认电脑时区与服务器执行时钟已分离；规则更新不更新可执行代码，不修改既有任务，也不在表单中途切版本。首版五个地区修复以实际可获取且通过验证的数据为门槛，不以版本标签或免费承诺代替验证。
