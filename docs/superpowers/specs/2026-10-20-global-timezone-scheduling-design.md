# 全球时区定时发布详细设计

日期：2026-10-20。状态：待用户审核，尚未编写实施计划或修改产品代码。

## 目标与边界

用户选择目标国家或地区、代表城市及时区，输入当地日期和时间，软件实时显示对应北京时间，并按确认后的实际时刻发布。无需人工计算时差，也不因电脑所在时区或夏令时而误排。

本轮交付详细设计。后续实现保留现有发布权限、授权范围、凭据、会员限制和排程执行方式；不重启 Worker，不新增云资源、收费 API、加速或存储服务。设计审核通过后再编写实施计划，不把本轮确认视为实施或部署授权。

首版包含新建定时发布、排程详情中的双时间查看与显式改期、已发布帖子中的时间核对、常用时区收藏。一次多账号发布仍使用同一个实际发布时间；按每个账号分别选择当地时间、周期性发布、自动推荐最佳发布时间不在范围内。

## 现有实现与兼容依据

- `SchedulePicker.tsx` 使用 `BeijingDateTimePicker`；`ComposerForm.tsx` 把北京时间输入经 `chinaLocalInputToISOString` 转成带 `Z` 的时间提交。发布检查文案目前固定为“已选择北京时间”。
- `composerService.ts` 接收 `scheduledAt`，保存排程时把 `timezone` 固定为 `Asia/Shanghai`。`Schedule` 已有 `scheduledAt` 和 `timezone` 字段，不需要新增表或回填旧数据。
- `scheduleService.ts` 已有创建和改期接口，改期省略 `timezone` 时保留原值；队列使用 `scheduledAt.getTime() - Date.now()` 计算延迟，不按时区名称重新换算。
- 日历日期工具、月周视图和拖拽按北京时间工作。`ScheduleDetailPanel.tsx` 编辑时间时固定转北京时间并写入 `Asia/Shanghai`；这部分需要接入统一时区编辑器，防止保存文本时覆盖原时区。
- `CalendarSchedule` 已包含 `timezone`。已发布列表投影和 `PublishedPost` 尚无该字段，需要增加可选返回字段，不能从账号或国家猜测原时区。
- 当前依赖树已有 Luxon 3.7.2，来自间接依赖；网页不能依赖这个偶然安装结果，实施时须声明经过检查的直接依赖并锁定版本。

## 方案选择

推荐复用既有排程字段，网页负责当地时间解析和预览，API 保存明确的实际时刻与有效时区标识，Worker 保持不变。这样既能保留目标地区信息，也无需重建队列或迁移历史排程。

仅网页换算的方案可以让发布时间正确，但现有 API 会把新排程时区仍记成北京，无法在详情准确恢复所选地区，因此不采用。另建时区排程服务、存储当地字符串并让 Worker 运行时换算，会增加旧任务重解释的风险，也不采用。

首版计划使用 Luxon 的 IANA 时区和候选偏移能力。相比另引入 Temporal polyfill，可复用仓库已有库版本并限制新增依赖面；不手写夏令时规则，不使用固定偏移量表替代时区规则。免费依赖并不替代安全检查：实施时核查版本、许可证、漏洞与网页体积，再锁定直接依赖。

## 时区选择界面

定时发布面板从上到下为：

1. “发布地区与时区”可搜索选择器。
2. “当地日期”和 24 小时制小时、分钟输入。
3. 必要时出现的重复时间选择或错误提示。
4. “目标地区时间”和“对应北京时间”双预览。
5. 紧凑的提交摘要，包含时区、日期和所选账号数量。

新建编辑会话默认北京时间 `Asia/Shanghai`，不依据 IP、账号国家、服务器时区或浏览器默认时区自动推断。用户修改电脑时区不影响表单。编辑现有任务以任务记录为准，不用默认值覆盖它。

选择器显示“国家或地区 / 代表城市 / IANA 标识”，例如“美国 / 纽约 / America/New_York”。国家不直接对应唯一时间；美国纽约、洛杉矶等必须分开选择。使用“代表城市”而不是承诺收录每座城市，允许按国家、中文名、英文名或 IANA ID 搜索。

常用区置顶，包括北京时间、纽约、洛杉矶、伦敦、巴黎、东京、新加坡、悉尼、迪拜；其余从完整地区时区目录搜索。数据采用版本化的 IANA 地理时区清单及 Unicode CLDR 中英文地区、城市名称，作为本地静态资源发布，保留来源和许可证。目录包含 UTC 入口，对历史别名建立明确映射，不通过自行改大小写生成标识。

目录仅决定可选项和名称，实际偏移由日期与时区规则决定。一个时区映射到多个地区时，各地区可以各自列出同一标识；收藏按标识去重。搜索不到城市时提示选择同一地区适用的代表城市，不能自动替用户选中。

常用收藏最多 8 个，存放在本机浏览器并按软件用户与工作区隔离，仅保存有效时区 ID，不保存凭据、帖子或排程时间。存储不可用时不影响排程；新建表单仍默认北京，不因收藏或上次选择而静默改变默认时间解释。

选择器不在未选日期时声称某地区有固定时差。双预览中的 UTC 偏移必须来自所选日期；不使用“当前时差”推算未来发布时间。两个预览都带完整日期，跨日明确标注“北京时间次日”或“北京时间前一日”，跨多天时显示实际日期差。

## 时间状态与切换规则

表单状态区分 `zoneId`、原始当地日期时间、解析结果和已确定的 UTC 时刻。解析结果只有以下情况：未完成、非法日期、不支持时区、当地时间不存在、当地时间重复、唯一有效时刻。

已确定的 UTC 时刻是提交和预览的共同来源。不要分别计算一份北京时间和一份提交值；不要把已是 UTC 的值再次当北京时间转换。

用户输入当地日期或时间时，按当前时区重新求解。修改任一输入会清除不再适用的重复时刻选择；新建或明确重选时间的输入粒度为分钟，生成时刻的秒和毫秒为零。加载旧任务时保留原实际时刻的秒和毫秒，纯切时区或文本编辑不得把它截断到分钟。

已有明确时刻时切换时区，保持该时刻不变，重新显示新时区的当地日期时间，并提示“仅切换显示时区，实际发布时间未变”。如果新地区恰好处于重复小时，用既有时刻定位正确那一次，不要求用户重新猜选。

尚未完成输入、输入无效或重复时刻尚未选择时，没有可保留的确定时刻。切换时区保留用户的原始输入并重新校验，明确提示“发布时间尚未确定”，不自动生成日期或选择某个重复候选。

日历、预览和提交不使用 `new Date(无偏移当地字符串)` 解析，也不依赖浏览器默认时区。严格验证真实公历日期、小时和分钟；不能把 2 月 30 日归一化成另一个日期。

新建排程日期控件的最早日期按目标时区的今天计算，不复用北京时间的今天，防止跨日地区被错误禁选。浏览既有任务不因最早日期限制修改输入；是否还能提交，最终按完整实际时刻及服务端当前时间判断。

## 夏令时与时区规则处理

转换工具先严格读取年月日时分，在指定 IANA 时区构建候选，再把候选转换回同一时区逐字段比对。Luxon 可能把缺失时刻顺延，只有回读年月日时分与原输入完全一致，才可继续接受。

对回读一致的候选调用 `getPossibleOffsets()`，去重并按实际时刻排序，再逐一校验回读结果：

- 唯一候选：接受，显示实际偏移及双时间。
- 两个候选：显示“当地时间出现两次，请选择”，给出“第一次”和“第二次”，每项包括偏移与完整北京时间；默认不选。
- 不存在或无法确认的候选：保留原输入并阻止定时提交，提示更换时间；不自动顺延、不用最近有效时刻替换。

不能假定变化总是一小时。测试涵盖半小时变化、45 分钟偏移、整日跳变及跨日期线。超过两个不一致候选、运行环境无法识别时区等异常一律阻止定时提交，不猜测。

按最终实际时刻验证未来时间，不能只比较日期或当地钟面时间。重复时刻中已过去的候选不可选；另一候选仍在未来时，用户可以明确选它。提交前重新检查，服务端继续以自身当前时间执行最终校验，不调整用户选择来规避“时间已过去”错误。

浏览器和服务器所用时区资料可能随运行环境更新。国家未来修改时区政策后，已确认的单次排程仍以已保存 UTC 时刻为准，不自动挪动；显示的当地时间按可用规则重新计算。不得宣传为未来政策变化后仍自动保持同一当地钟点的周期排程。

本机现有 Luxon 的只读样例检查已确认：纽约 `2026-03-08 02:30` 会顺延到 `03:30`，Lord Howe `2026-10-04 02:15` 会顺延到 `02:45`，所以“库返回有效日期”本身不等于用户输入有效。这些是转换边界样例，不是允许创建过去排程。

## 提交与草稿行为

新建定时排程请求仍提交 `scheduledAt`，值为带 `Z` 的 UTC ISO 字符串，另外传可选 `timezone`。例如纽约 `2026-10-20 20:00` 对应 `scheduledAt=2026-10-21T00:00:00.000Z`、`timezone=America/New_York`，北京预览为 `2026-10-21 08:00`。

API 不按 `timezone` 对 `scheduledAt` 二次换算。它验证 UTC 时间有效且在未来、时区有效、现有账号和会员权限满足要求，然后在原事务中保存。多账号发布的所有新增任务共享已确认的同一实际时刻和时区；不从各账号资料分别推测时间。

API 的 composer 输入增加可选 `timezone`；旧请求不传时保持 `Asia/Shanghai`。新建定时任务写入所选值，不再固定北京。普通创建和显式改期入口也使用统一的时区验证，改期省略字段继续保留原值；演示排程入口可保持现有北京语义，不作为本功能接入点。

时区校验使用受控长度、明确的 UTC 入口和运行环境支持的 IANA 命名标识，不接受模糊的 `CST` 或用户自造“UTC+8”文本替代城市时区。目录中的规范 ID 用于新提交；合法旧别名允许保留或在明确的新提交中规范化，不能批量改写旧记录。

发布检查不再无条件显示“已选择北京时间”。只有时间唯一有效或重复候选已明确选择时，才标记定时检查通过，并展示双时间。提交按钮直接使用已解析结果，不能根据是否有字符串就判有效。

切换“立即发布”不发送定时字段，现有立即发布逻辑不变。显式“保存草稿”不创建排程、不把时区塞进平台 payload。定时模式完全留空时保持现有保存草稿行为，并明确显示“未设置时间，将保存为草稿”；填了无效日期、缺失时刻或未选重复候选时阻止定时提交，不能悄悄降级为草稿。

首版不新增草稿排程元数据。草稿重新打开或复制内容时仍从未设置排程、默认北京开始，不复用旧帖的过去时间。当前会话内切换发布方式可保留尚未提交的表单，但不把它当成已经创建的排程。

## 日历和帖子详情

月历、周历、拖拽和时间范围查询继续按北京时间工作，界面明确标注“日历显示时区：北京时间”。不修改工作区时区或整站时区；同一个团队始终能按一致的日期分组查看。

排程详情显示两行：记录时区下的当地日期时间及偏移、对应北京时间。有效时区不在本地城市目录时仍显示标识和时间，不伪造城市。旧记录时区为空或无法识别时，保留 `scheduledAt`，展示北京时间并说明原时区不可用；纯查看不触发修复写入。

详情改期使用同一套地区选择与时间求解组件，但加载时从已保存的实际时刻生成输入。仅打开、切换展示时区、换语言或关闭详情都不发 PATCH、不取消任务、不重新入队。只改变展示时区且未改文本或实际时刻时，“保存修改”无写入，提示实际发布时间未变。

用户明确修改实际发布时间并保存时，才走原改期流程，同时保存所选时区；原有会员、角色及任务状态限制不变。只有文本变化时沿用原显式保存流程，保留原 `timezone`，不能把临时查看时区写回。已有改期流程内部的队列状态处理不在本轮重构。

日历拖拽仍表示按北京格子移动，必须明确其显示时区。拖拽请求继续只提交新的实际时间、不覆盖原 `timezone`；详情按原时区重新显示新时刻。不能误把拖到另一个北京日期理解为维持原地区同一钟点。

已发布帖子返回可选 `timezone` 并提供相同的双时间核对。旧响应缺少该字段时仅将北京时间标为当前显示，不声称知道用户当时选择的地区。实际发布完成时间与计划发布时间分别标注，不承诺社媒平台恰在秒级完成处理。

## 组件与数据职责

- `timezoneCatalog`：版本化地区、代表城市、规范时区 ID、别名与中英文搜索词。只读本地数据，无运行时第三方请求。
- `scheduleTimeZone`：严格解析、缺失和重复时刻检测、候选排序、时区切换保留时刻、北京格式化和跨日判断；纯函数，可注入当前时间测试。
- 通用日期时间输入：接收当地日期、小时和分钟，以及可访问名称；不能继续把非北京小时读成“北京时间小时”。保留 `BeijingDateTimePicker` 原用途，避免全局替换影响其他表单。
- `SchedulePicker`：负责选择器、日期输入、候选确认、双预览和错误展示，不直接请求发布接口。
- `ComposerForm`：持有排程状态及唯一提交值，接入发布检查与请求；不触碰平台授权或 payload。
- 日历详情与帖子详情：复用解析或展示工具，不各自实现偏移换算。
- API 时区校验工具：统一创建和改期的输入约束；复用现有 `Schedule.timezone`，不增加 schema migration。

选择器支持键盘搜索、上下移动、确认和 Escape，中文和英文文案完整；窄屏双预览纵向排列，不能横向溢出。错误与候选说明通过可访问标签关联到输入，预览在有效变化时适度通知，不在每次按键时重复长读。

## 旧排程和执行安全

上线不扫描或更新历史排程，不从 `timezone` 重新计算旧 `scheduledAt`，不补写猜测的国家或城市，不取消、重建或重新入队旧 PublishJob。发布凭据、OAuth 范围和平台发布选项不修改。

Worker 继续消费原有任务格式，只使用现有排程的确定时刻；新时区不是 Worker 的新必填字段。数据库已有字段足够，禁止借本功能运行 reset、db push、回填脚本或环境重建。

API 接受旧客户端缺省时区，新网页读取旧响应缺少可选信息时安全降级展示。实施后预计需要更新 API 和网页，原因是要真实保存所选时区，不能以“仅改文案”方式假装持久化；Worker 不需要新镜像或重启。

## 验收与回归

| 场景 | 必须达到的结果 |
| --- | --- |
| 北京 `2026-10-20 20:00` | UTC `2026-10-20 12:00Z`，北京预览同日 20:00 |
| 纽约 `2026-10-20 20:00` | UTC `2026-10-21 00:00Z`，北京次日 08:00 |
| 加德满都 `2026-10-20 20:00` | UTC `2026-10-20 14:15Z`，北京同日 22:15 |
| 纽约 `2026-11-01 01:30` | 两个候选 UTC 05:30Z 和 06:30Z，对应北京 13:30 和 14:30；默认不选 |
| 纽约 `2026-03-08 02:30` | 缺失时刻，不能顺延成 03:30 提交 |
| Lord Howe `2026-10-04 02:15` | 缺失半小时时刻，不能顺延成 02:45 提交 |
| 已确定时刻后切换纽约到东京 | UTC 不变，输入和双预览正确变化，无发布请求 |
| 一国多时区、跨年跨月和日期线 | 按城市时区分别转换，完整日期和跨日标注正确 |
| 偏移规则随季节不同 | 按排程日期计算，不能复用今天的偏移 |
| 非法日期、未知时区、输入不完整 | 无可用提交时刻，提示明确，不制造默认时间 |
| 电脑默认时区不同 | 同样输入、所选地区和候选产生同样 UTC |
| 旧客户端及旧排程 | 不传时区保持北京默认，查看旧任务不写数据或队列 |
| 旧任务原时间含秒与毫秒 | 纯查看、切时区及文本编辑不截断原实际时刻 |

边界日期作为转换单元测试使用；创建集成测试使用受控时钟，不能用过去日期绕过现有未来时间校验。增加普通时间、缺失时间、重复时间、文本编辑、草稿、立即发布、多账号、会员到期和工作区切换的真实组件及 API 回归。确认按钮、预览和最终请求的 `scheduledAt` 必须来自同一解析结果。

实施验证采用独立测试数据库和 Redis，不在腾讯云创建真实发布任务。完整测试、API 构建、网页生产构建及代码复核通过后才讨论部署；对旧记录、凭据和队列的保护以完整内容摘要和未写入断言验证，不能仅比较数量。

## 发布和回退约束

本轮不部署。后续部署需再次确认，仅允许 API 和网页，明确禁止 Worker 更新或重启；不更改密钥、OAuth 配置、权限申请、定时服务、实例规格或收费功能。

先部署兼容旧请求的 API，再部署网页，验证新排程保存和返回时区字段。旧 API 会忽略未知 composer 字段，不能把“时间能发布”当成时区已保存的证明。回退先网页、后 API，保留已合法创建的新排程及其实际时刻，不通过数据恢复撤销用户操作。

部署前后核对 Worker 容器、镜像和启动时间、原环境文件、七类受保护发布数据。没有 schema 变化就不执行迁移。时区资料和客户端运行环境的未来更新不自动改动已保存时刻；需要维护资料时纳入常规版本更新，不购买第三方时区服务。

## 参考资料

- [IANA 时区数据库](https://www.iana.org/time-zones)：地理时区及规则资料来源。
- [Unicode CLDR JSON](https://github.com/unicode-org/cldr-json)：地区与代表城市本地化资料来源。
- [Luxon API](https://moment.github.io/luxon/api-docs/)：时区、日期格式化和 `getPossibleOffsets` 的实现依据。
- [Luxon 时区说明](https://github.com/moment/luxon/blob/master/docs/zones.md)：默认时区及夏令时解析行为。
- [Temporal 时区与歧义说明](https://tc39.es/proposal-temporal/docs/timezone.html)：缺失时刻、重复时刻及确定时刻与当地时间的区别。
