# Facebook Page 评论与 Messenger 接入设计

日期：2026-10-07
状态：待用户审核；不是已实现或已部署的功能。

## 目标与范围

为 Social Scheduler 中已绑定的 Facebook 公共主页增加：帖子评论读取、人工评论回复、Messenger 会话与消息读取、人工消息回复、Webhook 实时接收。仅支持公共主页，不读取 Facebook 个人账号私信。保持软件名称、现有发布功能、Instagram 和 TikTok 接入不变。

首期不做自动回复、群发、广告评论、评论转私信、消息模板或超出标准消息窗口的发送。帖子管理只展示已有发布记录对应帖子的评论，不新增全主页帖子采集。

## 当前代码依据

- oauthProviders.ts 的 Facebook 默认主页权限为 public_profile、pages_show_list、pages_read_engagement、pages_manage_posts、pages_manage_metadata，尚无评论管理及 Messenger 权限。
- facebookPageCredentialService.ts 的凭据验证以发布为目标，不能直接作为互动能力判断。
- inbox/page.tsx 和 InstagramInbox 当前为 Instagram 专用；Instagram 接收数据表与路由也是平台专用。

## 推荐架构与取舍

采用独立 Facebook API 适配器、服务、路由和接收数据表，复用现有工作区鉴权、加密凭据、分页与界面样式。相比全面重构成通用多平台收件箱，这个方案对现有 Instagram 的风险更小；相比只轮询 API，它能接收后续实时消息。共用收件箱入口，内部以 Instagram/Facebook 标签切换，默认保留 Instagram 体验。

## 授权与能力状态

在社交账号页增加 Facebook 互动补充授权入口，不强制所有已有用户重新授权，不改动已有发布授权流程。补充授权保留原有发布权限；用户取消或授权失败时，现有凭据不被覆盖。若使用 Facebook Login for Business 配置，需要同步核实配置中所含权限，不能仅修改 OAuth 请求字符串。

计划权限：pages_show_list（选择主页）、pages_read_engagement 与 pages_read_user_content（读取适用帖子与用户内容）、pages_manage_engagement（评论回复）、pages_messaging（Messenger）、pages_manage_metadata（订阅）。实际调用所需组合须以当前 Graph 版本、主页任务及 Meta 返回结果验证。凭据获准权限、主页任务、应用访问等级、主页订阅分别展示，不能仅凭请求过的 scope 推定已授权。

分别维护发布、评论读取、评论回复、消息读取、消息回复、订阅能力。互动权限不足仅禁用相应功能，不把全账号标记为发布权限缺失。令牌整体失效才影响已有授权状态。能力未知与权限缺失分开处理；权限错误不能显示为“暂无评论”。

补充授权返回的主页必须与当前 providerAccountId 一致，所有操作先校验用户工作区权限、账号归属及平台。保持现有账号管理角色限制；团队成员读取及人工回复按现有收件箱角色规则执行并增加覆盖测试。

## 页面与接口

1. 社交账号：显示能力状态、补充授权和 Webhook 订阅状态。
2. 帖子管理：Facebook 帖子增加评论分页、刷新与人工回复，显示发送中、成功、明确错误。缺少有效帖子 ID 时提示无法读取，不猜测匹配帖子。
3. 收件箱：Facebook 标签内选择工作区和绑定主页，展示会话、消息、时间及人工回复输入框。切换账号取消旧请求或校验响应身份，防止跨账号显示。
4. 后端：工作区/账号作用域下新增能力查询、帖子评论查询/回复、会话查询、消息查询/回复路由。评论 ID 必须验证属于目标帖子；会话及收件人必须验证属于目标主页，不能由客户端任意提供目标 ID。

Graph 查询采用服务端保存的 Page token，跟随游标但不盲从任意 next URL。采用项目已有 Graph 版本配置，不另行硬编码新版本。发送超时或结果不确定不能自动重试，以免重复回复；返回“发送状态待核实”。

## Webhook、存储和隔离

新增独立 Facebook HTTPS 回调；GET 校验专用 verify token，POST 使用原始请求体验证 X-Hub-Signature-256。验证失败不处理，日志不输出令牌、签名密钥或完整消息正文。应用级订阅与主页 subscribed_apps 均必须核实；首期接收主页 feed 评论与 messages 事件，发送回显仅记为出站，不延长回复窗口。

使用独立 Facebook 接收事件、评论、会话、消息及同步状态表。唯一键包含本地账号与平台事件/消息 ID，支持重投去重。先持久化已验证事件再确认接收，异步处理支持有限重试和失败诊断。评论创建、编辑、删除事件均处理；未知事件安全忽略并记录计数。

按主页 ID 找到对应本地绑定账号，持久化数据始终带账号归属。若同一主页合法绑定多个工作区，分别产生隔离副本，不开放跨工作区读取；未绑定主页忽略。解绑只解除当前本地关系；若还有其他有效绑定，不取消全主页订阅。删除当前关系下缓存和敏感接收数据；事件迟到不得重新创建已解绑账号。

默认沿用现有接收数据 90 天保留策略，后台定期清理，并纳入现有数据删除流程。重新绑定不自动恢复已删除缓存。

## 消息政策与错误处理

首期仅允许标准 24 小时回复窗口内的普通人工文本回复。使用可信入站事件时间或可核实的 API 入站时间计算；回显、未来时间及缺失时间不创建窗口，无法确定时拒绝发送并提示去官方收件箱。后端强制执行，Meta 仍是最终裁决方。禁止自动加 HUMAN_AGENT 或其他标签绕过限制。

区分未授权、令牌失效、主页任务不足、应用访问等级不足、未订阅、限流、暂时失败、空列表与发送窗口关闭。展示必要诊断编号，不暴露秘密。读取失败保留旧数据并标明时间与失败状态，不伪装为刷新成功。

## 验证、部署与审核准备

测试先行：覆盖权限组合、取消授权保留凭据、跨工作区/账号拒绝、目标评论与会话归属、分页、请求竞态、签名验证、重投去重、删除、解绑及多绑定订阅隔离、消息窗口与发送结果不确定。回归现有发布及 Instagram 测试；新增数据库测试使用明确独立测试库，不接生产库。

先本地构建和测试，再备份、执行可兼容迁移、部署 API/worker/web。新增功能通过配置开关控制，默认关闭，测试通过后启用；回滚关闭开关并恢复应用镜像，不自动删除新增表。部署前列出变更和备份/回滚命令。

真实 Meta 权限配置、主页订阅、重新授权及公开客户启用按实际配置单独确认。使用指定测试主页及合法测试角色验证评论读取与人工回复、客户主动发起消息后读取与人工回复；真实发送前确认测试对象和文本。审核录屏展示授权、选择主页、读取评论、人工回复、消息读取及回复，使用真实测试数据，不制造成功状态。正式客户使用所需 Advanced Access 和审核由 Meta 决定。

## 完成标准

在受控测试主页上，能观察真实评论和 Messenger 消息，并经人工操作成功回复；API 和 Webhook 均有可核验状态，缺权限时正确提示，现有发布与 Instagram 行为回归通过。没有完成真实测试时明确报告限制，不宣布全面上线。
