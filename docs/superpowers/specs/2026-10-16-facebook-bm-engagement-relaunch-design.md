# Facebook BM 主页只读管理与互动恢复设计

日期：2026-10-16。状态：等待用户审阅设计；尚未开始产品实现或线上变更。

## 1. 已确认的目标和硬边界

用户需要在同一软件内查看已授权 BM（商务资产组合）下的公共主页，并切换已绑定公共主页读取、人工回复 Messenger 私信和帖子评论。不是个人账号私人聊天。

- BM 首版只读：名称、头像、主页链接、所属 BM、软件发布绑定状态、独立互动授权状态。
- 私信：会话和消息分页、手动刷新、符合标准回复窗口的人工文字回复。
- 评论：本软件真实发布记录下的评论分页、手动刷新、人工公开回复。
- Webhook 为及时更新补充；主动 API 读取不依赖 Webhook 成功投递。
- 原发布权限、OauthCredential 中的凭据、SocialAccount 发布绑定、发布配置 ID 和排程均不得被这套功能更新。
- Instagram 评论／私信入口与退役接口继续下线；不恢复 Instagram Webhook。
- 不加入点赞、自动回复、群发、陌生人主动私信、评论删除／隐藏、广告评论、BM 人员与资产分配、主页信息修改。
- 不新增收费资源；本阶段不发布 Meta 应用、不提交权限审核、不自动修改 Meta 权限或资产选择。线上部署另行确认。

## 2. 项目证据与方案选择

当前基线 fd2f78f。旧 Facebook UI、Graph 适配器和接收服务仍保留，但入口移除、路由未挂载，removedMetaEngagement 会返回 410。server.ts 未启动旧接收批处理。旧 facebookOAuthStore.save 会更新发布 OauthCredential，明确不能用于此次独立连接。

历史证据：Facebook Messenger 真正接收与人工回复曾成功；评论主动读取成功但真实 feed 通知未验收。两条开发者社区问题于本次查询仍未解决；不能宣称重新开发一定修复 Meta 投递。

比较三种方案：直接恢复旧共享授权最快但违反凭据不变约束；从零重写全部互动逻辑会扩大风险；选用独立授权存储、复用经回归验证的 Graph/权限/窗口校验单元，并重新接通 UI 与接收链路。

## 3. 凭据与数据模型

新增独立持久化模型及增量迁移，不改写、迁移或复制旧发布凭据：

- FacebookManagementConnection：工作区、授权发起用户、Meta 用户身份、签发应用 ID、加密用户 token、真实授予 scopes、到期时间、状态和版本号。一个工作区可有多条不同用户连接。
- FacebookManagedPage：connectionId、规范 Graph Page ID、BM ID/名称、主页名称/头像/官方链接、关系来源（owned/client/unclassified）、独立加密 Page token、真实 scope/task 检查状态、读取时间、授权状态。以连接和 Page ID 唯一，跨连接同主页按 ID 去重展示但不合并 token。
- FacebookManagementOAuthState：短时、一次性、绑定登录会话/用户/工作区/回调地址与连接版本；授权结果只保存到新表。callback 再查成员角色，校验应用、用户、所选资产和 token 身份，拒绝重放、错工作区、越权及并发覆盖。
- 新互动事件、评论、会话、消息和发送尝试表按 managedPageId 隔离；不自动导入或重新暴露旧收件箱存量数据。可复用旧解析/去重/排序逻辑，但依赖适配为新表，旧存储不恢复处理。
- 发送尝试记录工作区、主页、目标、客户端请求键、状态和 provider ID；禁止把 token 或正文记入诊断日志。

原 SocialAccount 与新主页只按同工作区、platform=facebook、规范 providerAccountId 精确关联，用于显示发布绑定状态及跳转。绝不根据名称猜测身份，不自动绑定/解绑发布账号，不把新 token 写回发布表。

软件内独立存储不意味着 Meta 端完全独立授权：同一 Meta 应用的权限仍可能关联。UI 说明这一限制；“断开管理连接”只在本软件停用并清除新连接凭据，不调用全应用权限撤销接口，不删除发布绑定。取消或失败的补充授权不能令原发布失效。

## 4. BM 只读目录与授权流程

owner/admin 可发起独立授权，明确列出用途和需要的权限；只访问用户明确允许的现有资产，不默认选择未来资产。已有发布登录配置及 scopes 不动，使用独立 BM/互动配置。

目录读取只使用新连接的用户 token。Graph 适配层读取可见 BM、其拥有/获分配主页以及当前用户可操作的主页，按 Page ID 交叉验证，不能仅凭“BM 包含该主页”推断个人具有消息或评论权限。owned/client 关系区分显示；缺失 BM 关系归为“未识别 BM”，不伪造归属。主页列表分页需覆盖 20 个及以上，不以第一页作为完整列表。

候选目录接口是 User businesses、Business owned_pages/client_pages 及用户 Pages 列表；实现前必须逐项核对目标 Graph 版本、官方文档、字段与 token 类型。官方 SDK 存在接口不等于本应用已获得权限。受限字段返回局部不可用，不静默退化为“没有主页”。

Page token 只从独立 OAuth 结果和官方支持的读取流程获得；缺少 token/task/身份时，该主页可展示目录信息但不能互动。business_management 不是消息、评论能力证明。默认最小用途为 public_profile、business_management、pages_show_list、pages_read_engagement、pages_read_user_content、pages_manage_engagement、pages_messaging、pages_manage_metadata；这是待逐项验证的用途清单，不是已获批声明，也不请求 pages_manage_posts。后台配置更改和实际新增授权须在操作前说明真实资产范围并取得确认。

目录 GET、用户点击刷新和短时缓存不修改 Meta 资产。每次分页以工作区内服务器存储的连接为根；不允许客户端传任意 BM/Page ID 或 Graph URL访问。游标限长、固定 host/path、限制单次页面大小与并发。

## 5. UI 和 API 边界

- 左侧“BM 主页管理”：工作区、连接、BM 筛选与名称搜索；支持主页卡片/列表、访问官方主页、安全状态、最后成功读取时间、刷新、连接/断开管理授权。断开需明确确认影响仅新管理/互动数据访问。
- 左侧“Facebook 收件箱”：工作区、已绑定公共主页、会话、消息；可从 BM 页面携带经校验的选择跳转。未发布绑定的目录主页仅提示去现有社交账号流程绑定，首版不自动创建发布账号。
- 帖子管理 Facebook 评论入口：只对同工作区真实发布记录、可精确匹配独立互动主页且授权可用的帖子显示。已删除发布账号、缺失原帖 ID、模拟发布记录均不可发回复。
- 同一个主页经多个管理连接可见时，管理员明确选择互动连接；不静默切换到另一人的授权。失效时保持只读错误提示，不回退到原发布 token。
- viewer 仅查看；owner/admin 管连接；owner/admin/editor 可人工回复。所有鉴权在服务器复核。
- 新 BM/连接 API 使用独立命名空间；恢复 Facebook 私信、评论路由时精确放行 Facebook，继续阻断 Instagram 退役路径。旧补充授权入口不得仍能修改发布凭据：停止旧写入路径，客户端改走新连接流程。
- 界面中英双语，适应手机宽度；发送时显示主页名称与收件目标，切换工作区/主页/会话清空草稿与请求上下文，迟到结果不得污染新视图。正文安全文本渲染，不放入 localStorage/分析日志。

## 6. 读取、发送和通知

主动读取：进入视图或点击刷新查询 Graph，保留分页；仅当前可见视图每 30 秒刷新一次，禁止后台全 BM 无限制轮询。读失败保留本上下文上次成功数据、标注陈旧时间和错误；初次错误不显示成成功空列表。切换上下文不保留前一主页正文。

私信仅回复用户主动联系后的标准 24 小时窗口；发送前由服务器依据当前授权、会话身份、可信入站时间复核，echo/主页发出的消息不延长窗口。时间未知或过期则拒绝并提供官方收件箱入口。首版仅文字，不下载附件。

评论发送前重新验证帖子所属主页、评论所属原帖、工作区与角色。无 Webhook 时直接 API 查询仍可工作。首版不提供任意外部帖子 ID 输入或原生历史帖子浏览。

发送使用客户端请求键及服务器唯一约束防同次重复提交。超时/连接中断等结果未知时显示“发送结果未知，请核对”，绝不自动重试；明确失败与未知分开，收到确认 provider ID 才显示发送成功。

Webhook：在通用 JSON 中间件之前挂载 Facebook 原始 body 路由；校验签名、challenge、内容大小。仅投递给当前活跃且用户明确启用通知的管理主页，按工作区独立保存，事件去重/乱序/删除处理、持久化成功后确认；暂存失败返回可重试错误。订阅按钮是明确操作，不在 GET 中自动变更 Meta 订阅。

多个工作区共用同一 Meta Page/app 时订阅为共享外部资源：去重订阅，断开单个本地连接不取消其他用户仍依赖的订阅；首版不自动执行 Meta 端取消订阅，停用本地接收映射并告知管理员仍可能存在上游订阅。

接收持久队列的处理由 API 进程管理的有界任务泵执行，使用数据库租约支持多实例，启动/退出随 API 生命周期；不向原发布 Worker 加入任务、不改变其并发、凭据检查和排程。定时任务重入保护，崩溃后可恢复。不能仅恢复 webhook 路由而遗忘事件处理。

## 7. 安全、保留与状态呈现

token 只在服务端加密保存，错误只返回安全分类和诊断 ID，不记录原始 Meta payload、正文、签名或 secrets。新接收正文默认滚动保留 90 天，附件二进制不落盘；清理仅限新互动表，不处理发布数据或旧接收数据。用户断开立即停止访问/接收；工作区删除纳入现有删除流程。

状态分别表示：发布绑定、目录授权、评论读/回、消息读/回、订阅配置、最近真实通知。已授予 scope 不等于高级访问审核通过；模拟测试不标为真实通知成功。权限失效只影响新连接，不更新原 SocialAccount 发布状态。

## 8. 验收与部署门槛

1. 独立测试库验证增量迁移、跨用户/工作区隔离、20+主页完整分页、重复连接去重、撤权、OAuth 重放/并发与断开。测试绝不使用生产库。
2. 授权成功/失败/取消、读取/刷新/回复/断开均断言原 OauthCredential、发布绑定、scope、登录配置与排程未被改写。
3. UI 真交互覆盖切换上下文迟到请求、错误与空结果区分、viewer 禁发、双击防重、未知结果、移动端和中英文。
4. 通知测试覆盖错误签名、重放、乱序、进程中断恢复、队列处理、多个工作区隔离和共享订阅；Instagram 全部退役接口仍返回 410。
5. 在全套测试和生产构建通过后，人工验收与单独获准的目标主页执行真实私信收发、评论读取回复；不重复发已有测试评论。发送内容与目标操作前确认。
6. API 读取验收与真实 Webhook 验收分开记录。真实通知未到达时报告未解决，不归咎网络或宣称 Meta 故障；手动读取仍须可用，保留安全诊断供 Meta 跟进。
7. 部署须另行授权。只规划新 API/Web 和必要的新增表迁移，不重启原 Worker，不改权限/凭据环境文件；先受限备份、迁移验证、保留旧镜像，核对运行标识与配置摘要。回滚代码不删除新表和数据。
