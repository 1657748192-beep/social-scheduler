# Instagram REC3 独立单次人工回复资格设计

日期：2026-10-23  
状态：书面设计待审阅；不是实现或部署授权。  
适用对象：Social Scheduler 的 mooyamcosmetic Instagram 独立互动接入。

## 1. 已确认的目标与边界

同一个个人测试账号发送新的 `SS-IG-DM-1023-REC3` 私信后，经指定记录核验，为该来信开放一次人工回复机会。不是解锁整个会话，也不是让所有新来信自动获得机会。

强制约束：

- 旧 REC1、REC2 次数、发送尝试、回执、请求键和防重标识不变；不回填、不重写、不清除旧发送记录。
- REC3 最多触发一次应用层发送调用；重复点击、并发、新请求键、进程中断、重新同步或重新授权都不能增加次数。
- 失败、超时和结果未知均不自动重试、不释放已占用资格。不承诺远端恰好投递一次；软件保证不会为该资格主动再次发送。
- 保留授权、管理员、工作区、账号、独立连接、回复窗口、删除、保留期和限流检查；防重资格不替代这些检查。
- Webhook 保持关闭，不引入 Worker 任务、自动回复或后台发送队列，不新增收费资源或权限。
- 本轮仅编写本地设计文档；不修改产品代码、数据库、配置或线上数据，不请求 Meta，不部署、不重启、不发送、不提交审核。

## 2. 当前实现与问题来源

当前 `sendAttempts.ts` 的受限发送准入按 `hash([kind, targetId])` 查询同一连接的历史尝试。私信的 targetId 是接收者，即个人测试账号的 Instagram scoped ID，而不是某条来信的消息 ID。任何历史状态都消耗这个受限目标的机会。

`replyRecording.ts` 目前仅识别 REC1、REC2，固定文案和来源记录一一绑定。`engagement.ts` 用同一目标哈希判断机会是否使用；`replyReceipts.ts` 与收件箱已回复状态依赖旧目标哈希、时间及原始回执证据。直接更改哈希或忽略旧历史，会破坏这些关联。

因此选择新增独立资格层：仍使用旧格式记录发送目标和载荷，另以原始来信唯一身份约束 REC3 的一次机会。REC1、REC2 继续使用原路径。

## 3. 方案取舍

1. **采用：新增持久化资格记录，关联唯一原始发送尝试。** 能保留旧记录格式与回执读取规则，同时对指定新来信建立更精确的一次性约束。
2. 不采用：直接把所有 targetHash 改成消息级哈希。需要同时改历史回执和删除关联，容易造成旧数据语义变化。
3. 不采用：只新增配置开关、忽略旧尝试或清空次数。无法可靠抵御并发、重启和重复请求，也违反已确认边界。

这是发送准入与回执关联的安全边界设计。实现前需要完成书面设计审阅，再编写实施计划；当前不进入实现。

## 4. 资格数据模型（拟新增，尚未迁移）

拟新增 `InstagramReplyRecordingGrant`，不改写旧发送尝试表中的既有行。

| 数据 | 用途 |
| --- | --- |
| id、workspaceId、appId、providerAccountId | 资格 ID 与租户、应用、接收账号的稳定命名空间 |
| incomingKey | 下述原始来信身份的域隔离摘要，数据库唯一约束 |
| accountId、userId | 指定本地账号及允许手工操作的管理员 |
| connectionId、connectionVersion | 本次核验所依据的独立连接版本；仅作有效性约束，不提供新的次数 |
| sourceRecordId、providerEventId、actorId、conversationId、occurredAt | 已验证的来信绑定；正文不复制到资格表 |
| predecessorAttemptId、predecessorProviderId | 上次已确认原始回复的证据绑定 |
| marker、payloadHash、expiresAt | 固定 REC3 场景、固定回复载荷和截止时间 |
| state、attemptId、claimedAt、closedReason、createdAt | 单次占用及关闭状态；attemptId 唯一，一个资格只能关联一个原始尝试 |

incomingKey 定义为有版本和用途前缀的规范序列摘要：

`SHA256(JSON(["ig-recording-message-grant-v1", workspaceId, appId, providerAccountId, providerEventId]))`

- 使用真实 Instagram 消息 ID，不使用正文、录屏标签、请求键或本地 sourceRecordId 作为唯一身份。
- actorId 和 conversationId 是不可变、必须匹配的验证字段，而不是可用来创建第二份资格的替换参数。同一消息 ID 的不同发送者/会话绑定直接拒绝。
- incomingKey 不包含本地账号 ID、连接 ID 或连接版本，避免重新建本地映射、重同步或重新授权使同一消息再次获得次数。
- 本轮不允许跨工作区迁移资格，也不开放其他账号或管理员。
- 资格不能因来源记录过期、删除或发送尝试清理而级联删除并重新变成可用。具体隐私处理见第 10 节。

## 5. REC3 配置与受控核验

在现有受限配置中新增可选、严格校验的 REC3 绑定，保持 REC1、REC2 原配置不变。缺失、无效、歧义、版本不匹配或未准备好时默认关闭，不回退成非受限发送。

REC3 固定入站标识：`SS-IG-DM-1023-REC3`，标识只用于寻找候选，不能替代身份验证。

固定出站文案：

> Social Scheduler Instagram messaging reply test REC3. This reply is for app review demonstration only.

在未来获准读取/准备时，必须核验：

1. 独立授权账号确为 mooyamcosmetic，工作区、应用、接收账号、管理员、连接及版本均匹配。
2. 候选为真实 inbound 消息；原始消息 ID、发送者、接收者和会话归属一致，消息未删除，未超出现有保留期和回复窗口。
3. 候选唯一；重复标识、缺失消息 ID、不同原文时间或身份冲突时停止，不自动选最新或任意一条。
4. 同一发送者的上一笔实际发送有唯一、原始、已确认成功的有效回执；不能用复制回执或前端“成功”文字证明。
5. REC3 的平台来信时间严格晚于上一笔原始确认完成时间。时间相同、来源不可信或有歧义时不开放；不以同步接收时间替代平台时间。
6. 同一目标存在任何尚未厘清的 pending/unknown 发送，或历史删除/清理导致无法证明安全时，不准备资格，不推断“应该已经成功”。不得自动改写历史状态来解除阻塞。
7. 如果证据表明 REC3 已经被官方或其他渠道回复，先停止并人工核对，不把它当作未回复录屏消息。
8. 截止时间取现有平台策略、原始来信允许窗口及录屏配置截止的最早值，不因同步、刷新或重新登录延长。

只有被精确核验的这一条消息才创建 available 资格。只读页面打开、列表刷新和普通同步不得创建资格；重复运行准备程序只返回同一资格，并不得覆盖其状态、截止、载荷或已关联尝试。

未来的 Meta 读取必须有明确允许的 GET 路径、请求数量边界、限流即停及脱敏日志；本设计轮不执行这些请求。

## 6. 人工发送准入与并发控制

保留现有手工回复入口和请求键。客户端不能自行提交或选择任意可用资格；服务端依据已授权的来源记录解析 REC3 资格。

采用固定锁顺序：现有独立连接锁，然后资格行锁。资格唯一约束与 attemptId 唯一约束是数据库后盾，前端禁用按钮不是唯一防线。

一次人工请求的处理顺序：

1. 完成现有登录、工作区、管理员、账号、配置、内容、有效期与权限检查。
2. 在一个数据库事务内锁定连接及资格，重新验证来源绑定、截止、前驱成功证据和未知结果阻塞条件。
3. 查询请求键：若已被旧记录或其他输入使用，拒绝或返回其真实既有状态，不能把旧 REC2 请求键关联到 REC3。
4. 仅当资格 available 且没有 attemptId 时，原子创建一条 pending 发送尝试并绑定资格，资格进入 claimed。旧格式 targetHash/payloadHash 保留；不修改 REC1、REC2。
5. 提交事务，之后才能执行远端操作。不会持有数据库锁等待 Meta。
6. 发送前再次执行现有本地权限、删除、窗口、资格绑定和连接检查。该步骤失败则关闭本次资格，不释放重新尝试。
7. 原始获准请求最多调用一次既有 sendMessage；发送层不得对此 POST 自动重试、重定向重投或后台补发。
8. 按回执更新原始尝试状态。后续重复请求只读取资格所绑定的同一 attempt，不创建新 attempt，也不再次发送。

回执终态写入时，原始尝试及资格状态应在同一数据库事务内更新，并使用 pending/claimed 条件更新防止覆盖既有终态。该事务失败时不把资格恢复为 available；读取以已绑定原始尝试的持久化证据为准，证据不完整则显示待核查，不能只相信某一张表的 sent 字符串。

不能以“同一目标出现过旧成功”为理由直接拒绝已获资格的 REC3，但这只适用于明确验证并持久化占用的 REC3 分支。其他记录仍进入原受限准入逻辑；若无法证明分支资格，必须关闭，不能降级至无录屏限制的通用路径。

首次请求与重复请求使用相同连接串行边界，资格占用期间其他候选不得在同一受控目标上并发发送。未来新资格的准备与准入也必须检查未确认历史，不能跨资格同时发送。

## 7. 状态与中断行为

| 状态 | 可发送 | 后续行为 |
| --- | --- | --- |
| available | 满足所有检查时可人工操作一次 | 原子占用后进入 claimed |
| claimed | 否 | 仅原始请求可继续一次发送；重复请求显示发送中/待核查 |
| sent | 否 | 有有效原始回执，显示已回复和对应气泡 |
| failed | 否 | 已消耗，展示明确失败，不重试 |
| unknown | 否 | 已消耗，展示结果待核查，不重试 |
| closed | 否 | 过期、撤权、删除或准备失效；无重新开放操作 |

资格是否已消耗由 attemptId/claimedAt 决定，不能只凭易变化的前端 state 判断。

- 事务提交前中断：没有发送，也没有有效占用；后续仍须走完整准入。
- 事务已提交、远端调用前中断：资格仍被消耗；重启不续发、不释放。即使可能零投递，也以防重为先。
- 远端可能已接收、响应超时或回执写入失败：资格保持占用并显示 unknown，不自动补发。
- 持久化 sent 回执后刷新失败：保留发送成功；只提示详情刷新失败。
- 长期 claimed 不通过 Worker 或定时器重新派发。读取时按待核查展示，不通过超时释放锁定资格。
- 重新授权使现有版本绑定失效：不会生成第二资格或自动重新绑定。原消息的已占用资格永久不能再次发送；未占用资格需要另行显式核验，当前 REC3 流程选择关闭而不是自动续期。

## 8. 回执、聊天回显和“已回复”

原始回执读取除原有授权、时间、载荷和删除约束外，对 REC3 必须确认：

- 资格 incomingKey 及来源绑定匹配当前消息。
- attemptId 指向该资格唯一原始尝试，工作区、连接、版本、targetHash、payloadHash 均匹配。
- status 为 sent，providerId 合法，且符合原始发送证据检查；任何旧 REC2 回执或重复请求的复制结果都不能代替。

仅凭同一发送者、相同文字、较新时间或会话中存在一条主页回复，不得把 REC3 标记为已回复。

实时确认成功后沿用本次已上线的右侧立即回显与一次滚动定位；重复读取按 providerId 去重。重载后从资格绑定的原始尝试恢复确认文案，不写入或臆造其他聊天正文。

REC3 尚未发送时，列表和详情必须按新的 inbound 基准显示待回复，旧 REC2 历史气泡仍可展示但不能让新消息显示已回复。后续若出现更晚新来信，“已回复”仍应依据它之后的有效原始回执计算，不能把 REC3 成功泛化到未来来信。

同一会话的列表条目可以复用，但受控同步后选择依据必须是已核验的 REC3 来源；不能继续拿旧 REC2 的 sourceRef 进入录屏发送分支。列表条目 ID、来源消息 ID 与资格 ID 是三个不同概念。

保持 source/case、工作区、账号、登录会话、连接版本和访问失效围栏。权威删除及空响应优先；不得用立即回显恢复被删除或已无权查看的内容。

## 9. 前端表现

- 仅指定 REC3 来源显示固定文案和“此条新来信仅可人工回复一次”。普通私信不因该设计开启回复能力。
- 点击后立即显示 Sending，按钮禁用；跨标签页仍由数据库准入保证次数。
- 确认成功显示右侧气泡、Replied 及机会已使用。
- unknown/claimed 仅提示去官方核查，不出现“重新发送”“重置机会”按钮。
- 回复已发送但刷新失败时单独提示，不把发送成功改成发送未知。
- REC1、REC2 保留各自真实已使用/过期状态，不显示新的可用机会。

## 10. 隐私、删除与保留期

新增资格只保存必要绑定和防重元数据，不保存访问令牌、客户正文或可复用凭据。日志仅输出脱敏诊断与状态，不输出消息、身份原值或完整配置。

不能用永久保存可识别客户数据来换取防重。新表需要接入现有删除与保留机制：

- 来源、授权、账号或用户删除/过期后立即失去可发送及可回显资格。
- 清理资格可识别字段及回执引用时保留最小关闭标记，不允许把清理理解成“没有用过”。摘要仍作为受保护的假名数据处理。
- 不设置会阻塞现有删除流程的级联/RESTRICT 外键；来源或尝试消失不能使资格可重建为 available。
- 最小关闭标记最终删除时，必须保证原始来信已过现有允许窗口及保留期，并且任何重同步都因原始 occurredAt 不合格而无法重新准备；不能按本地新 receivedAt 重新计时。
- 若旧尝试已被匿名化，无法可靠确认前驱/未知发送归属，则新资格关闭，不自动放宽。
- 执行现有生命周期清理属于隐私规则；本次发布不得借此重置或批量改写旧 REC1、REC2 数据。设计测试需验证两者没有混淆。

## 11. 兼容、发布及回退设计

实现范围预计涉及新表及加法迁移、REC3 配置解析、资格准入、发送尝试关联、受控同步准备程序、回执读取、列表/详情状态及录屏提示。不是只改前端按钮。

- 旧配置没有 REC3 时行为不变；无新资格时关闭 REC3。
- 新表初始为空；不为 REC1/REC2 自动生成资格，不迁移其次数。
- 不修改旧 targetHash 算法、旧 requestKey 唯一性或评论准入。
- 未来发布需先授权并应用加法迁移，再部署支持新配置的 API/网页。仅重启 API，Worker/Webhook 不动；不新增订阅、权限或凭据。
- 新配置默认关闭；只有受控只读核验、原文同步、资格检查及快照均通过后才准备指定 REC3。准备与发布都不发送回复。
- 发布前后对权限、凭据、排程、旧发送尝试及运行容器进行脱敏快照核对；允许变化必须仅限已批准的加法迁移、新 REC3 同步/资格及发布必要配置。
- 关闭 REC3 开关即拒绝新发送；保留已占用资格和新表。不得在回退时删除资格、撤销占用或执行破坏性降级迁移。
- 旧 API 的配置解析严格，回退前必须移除仅 REC3 新字段并保留旧配置原值；不得让旧版本带不认识的配置启动。回退只能使 REC3 更严格关闭，不能重开旧目标。

## 12. 必须通过的验证清单

实现时采用先失败后通过的测试，并运行全量回归、API/网页构建及独立代码复核。至少包括：

1. 同一发送者的 REC3 在上次原始确认回复之后可独立准备，REC1/REC2 行级快照不变且不能重发。
2. 重复标识、伪造 sourceRecordId、同一 providerEventId 的身份冲突、错账号/应用/工作区/管理员/连接均拒绝。
3. 来信早于或等于前驱确认时间、无原始回执、历史 pending/unknown 或已清理导致证据缺失时关闭。
4. 重复同步、重建本地记录、连接版本变化和重新授权均不能产生第二个 incomingKey 资格。
5. 同请求键重试、新请求键、双击、多标签页、独立 executor、并发进程最多创建一个原始尝试，并最多调用一次模拟 provider 发送。
6. 旧 REC2 请求键不能被 REC3 使用；其他普通记录不能从 REC3 特殊分支获益。
7. 在占用前、提交后发送前、远端接收后及回执持久化时注入中断，均不发生自动补发或资格释放。
8. sent/failed/unknown/claimed/closed 的重载行为符合状态表；错误 providerId 不得显示成功。
9. 旧 REC2 回执、复制回执或不同载荷不产生 REC3 已回复/气泡；新 REC3 原始成功回执立即回显并去重。
10. 更晚新来信使会话恢复待回复，不自动获得资格；滚动、历史加载、中英文及刷新失败提示保持正确。
11. 权限撤销、过期、删除、历史清理及连接变更立即关闭发送/展示；清理不导致重开，删除不被回显复活。
12. 缺失/无效 REC3 配置安全关闭；旧配置、评论、REC1/REC2、普通发布与排程保持回归通过。
13. 受控操作脚本只能读取批准 GET、同步指定原文和准备指定资格；不得包含发送、重置旧行、开启 Webhook 或重启 Worker 的操作。

本轮没有执行上述实现测试，也没有确认线上 REC3 的原始消息 ID、前驱回执、时间顺序或可用性。它们必须在后续明确授权的核验步骤中证明，不能以本设计文档代替事实。
